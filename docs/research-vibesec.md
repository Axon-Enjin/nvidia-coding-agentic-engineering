# Sandbox feasibility: VibeSec

**Date:** 2026-09-30
**Status:** Draft
**Owner:** Project owner
**Last reconciled:** 2026-09-30

This note verifies source claims for the owned synthetic fixture demo. Documentation supports a filesystem-based branch workflow, but access, execution, network controls, and model behavior still require runtime proof. No authenticated or paid API was called, dependency installed, or person contacted.

| Claim | Evidence | Limit | Implication |
|-------|----------|-------|-------------|
| Branches share a captured filesystem, then evolve independently. | [Branching workflows](https://docs.tokenfactory.nebius.com/sandboxes/sdk/python_sdk/branching) defines a snapshot of files and directories after a command; repeated runs from the same parent produce independent children. | This establishes filesystem checkpoints. It does not establish preservation of RAM, live processes, sockets, or database connections. Identical files do not guarantee identical network, clock, or random inputs. | Persist fixture data to files and restart its service within each branch execution. Prove parent and sibling independence using hashes and branch UUIDs. |
| A session advances its current image after execution; reusable checkpoints must survive execution. | [SDK repository](https://github.com/nebius/contree-sdk) explains versioned images and automatic session advancement. [Image reference](https://docs.tokenfactory.nebius.com/sandboxes/sdk/python_sdk/reference/image) documents SDK `disposable=True` by default, explicit timeout, and output truncation. | The [REST instance reference](https://docs.tokenfactory.nebius.com/api-reference/sandboxes/instances/spawn-a-new-container-instance) has a different disposable default, `false`. | Set `disposable=False` explicitly for parent and child evidence images; set execution time and output limits explicitly. Preserve image references rather than relying on a mutable session pointer. |
| Nebius documents VM-level workload isolation. | [Sandbox overview](https://docs.tokenfactory.nebius.com/sandboxes/overview) states VM-level isolation and Git-like branching. It marks the service Beta, limits simultaneous operations to 50, and gives untagged unreferenced checkpoint images 180-day retention. | These are provider statements, not an independent escape test or an availability guarantee. Isolation does not establish denied outbound network access. | Record the provider boundary separately from the application policy. Retain/export required evidence and handle capacity or service failure. |
| The REST schema exposes a networking configuration, but the high-level SDK run signature lacks a network argument. | [REST instance reference](https://docs.tokenfactory.nebius.com/api-reference/sandboxes/instances/spawn-a-new-container-instance) shows `networking.enabled`, UID/GID, and resource limits; [SDK image reference](https://docs.tokenfactory.nebius.com/sandboxes/sdk/python_sdk/reference/image) lists the run parameters. | The inspected rendered docs do not establish an egress allowlist, DNS policy, incoming port exposure, or the exact effects of disabling networking on loopback. | Verify the supported client path and deny-egress setting. Test fixture loopback connectivity and denied external access before treating sandbox isolation as a complete target boundary. |
| Current SDK construction delegates credentials and transport to `contree_client`. | [Getting started](https://docs.tokenfactory.nebius.com/sandboxes/sdk/python_sdk/getting-started) takes an already constructed client; auth, base URL, retries, and timeouts belong to that client. [Running commands](https://docs.tokenfactory.nebius.com/sandboxes/sdk/python_sdk/running-commands) explains that `preserve_env=True` writes supplied environment into image metadata. | Some older examples may target a different interface. A usable sandbox endpoint and account access were not verified. | Resolve and pin actual client/SDK versions during the spike. Keep provider keys in the controller; never preserve secrets in an evidence image. |
| Token Factory exposes an OpenAI-compatible inference endpoint. | [Quickstart](https://docs.tokenfactory.nebius.com/quickstart) uses `https://api.tokenfactory.nebius.com/v1/`, bearer API key, and `/chat/completions`. [Public serverless](https://docs.tokenfactory.nebius.com/public-serverless) warns that public processing regions can move. | Regional cookbook URLs do not guarantee continued public endpoint routing. | Start with the documented global base URL and verify the selected model's endpoint. Record the request model, completion status, token usage, and latency. |
| NVIDIA Nemotron candidates appear in first-party examples; no live catalog pin is established here. | Nebius [Nano example](https://github.com/nebius/token-factory-cookbook/blob/main/models/nemotron/nemotron3-nano-30b.md) uses `nvidia/nvidia-nemotron-3-nano-30b-a3b`; [Super](https://github.com/nebius/token-factory-cookbook/blob/main/models/nemotron/nemotron3-super-120B.md) uses `nvidia/nemotron-3-super-120b-a12b`; [Ultra](https://github.com/nebius/token-factory-cookbook/blob/main/models/nemotron/nemotron3-ultra-550b-a55b.md) uses `nvidia/Nemotron-3-Ultra-550b-a55b`. | The Nano [Playground link](https://tokenfactory.nebius.com/playground?models=nvidia%2FNVIDIA-Nemotron-3-Nano-30B-A3B) differs in capitalization. The [catalog](https://tokenfactory.nebius.com/models) supplies no static text; examples do not prove current account availability. | Select the exact case-sensitive ID from the authenticated [models API](https://docs.tokenfactory.nebius.com/api-reference/models/list-models) during the first spike. No model is pinned by this note. |
| Structured output and tool calling require selected-model validation. | [JSON guide](https://docs.tokenfactory.nebius.com/ai-models-inference/json) documents `json_schema` and `json_object`, model-card JSON support, and model-dependent limitations. [Tool guide](https://docs.tokenfactory.nebius.com/ai-models-inference/function-calling) says the model proposes calls; application code executes them. Nano/Super examples claim both capabilities; Ultra claims tool calling. | Capability claims do not establish schema adherence, tool accuracy, truncation handling, or safety for this fixture. | Validate schema and allowed values in application code. Reject malformed, unknown, or out-of-budget actions. Test refusals and incomplete responses. Never execute raw model output. |
| Hackathon runtime and deadline are documented; Sandboxes wording is inconsistent across retrieved representations. | [Rules](https://nebiusglobalaihackathon.devpost.com/rules) require one NVIDIA open-source model plus a Token Factory inference runtime call or Nebius AI Cloud compute. Fresh page text says the coding track works "in Token Factory"; indexed results for that URL and [overview](https://nebiusglobalaihackathon.devpost.com/) say "in Token Factory Sandboxes". | These observations cannot establish which representation is newest. Sandbox use should not be dismissed based on the shorter wording. | Keep Sandboxes in this track's plan and recheck before submission. Deadline: October 30, 2026, 10:00 am PDT, equivalent to October 31, 2026, 1:00 am Manila. |
| Submission needs a working artifact beyond a prerecorded report. | [Rules](https://nebiusglobalaihackathon.devpost.com/rules) request a working demo/test build, public licensed repository, setup README, public YouTube demonstration under three minutes, and tool feedback. Judge access must continue through December 15, 2026. Tavily bonus requires its functional runtime call. | Optional Tavily is not a base eligibility requirement. A replay does not prove a live inference integration. | Capture live provider evidence and provide reproducible setup. A read-only report can present evidence, with a functioning test build available to judges. |

## Runtime proof still needed

1. Resolve sandbox access and client versions; import a pinned fixture image and run it successfully.
2. Create one parent and two divergent children; verify retained files, parent hashes, UUID lineage, and independently restarted fixture processes.
3. Prove supported denied-egress configuration, loopback behavior, timeout/cancellation, output caps, and cleanup using harmless checks.
4. Retrieve exact available NVIDIA model ID; verify one live inference, schema validation, bounded tool proposals, provider failure handling, and usage accounting.
5. Export evidence with timestamps, immutable fixture identity, sanitized logs, and explicit incomplete/failure states. Keep runtime results distinct from this source review.
