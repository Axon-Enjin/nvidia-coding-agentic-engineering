# VibeSec competitive landscape and positioning

**Researched:** 2026-10-13
**Status:** Product research, not a claim that VibeSec works
**Scope:** Public first-party product documentation, project repositories, and this repo's draft requirements. Products change; recheck before making public comparative claims.

## Executive finding

The broad concept is already a crowded market. AI pentesters such as XBOW, RunSybil, Shannon, and Strix claim or document autonomous testing with exploit evidence. XBOW explicitly supports planted canaries and fix verification. StackHawk explicitly tests cross-user object authorization with two profiles and distributes skills for Codex and other coding agents. Consequently, **AI testing, proof-of-exploit, cross-user BOLA detection, canary validation, fix retesting, and a skill wrapper are not novel product claims**. [XBOW canaries](https://docs.xbow.com/console/how-to/validate-with-canaries/), [XBOW reports](https://docs.xbow.com/console/reference/reports/), [StackHawk multi-profile testing](https://docs.stackhawk.com/hawkscan/business-logic-testing/), [StackHawk agent skills](https://docs.stackhawk.com/ai-security/agent-skills/).

A credible hackathon angle is a **small, inspectable security experiment**: an owned vulnerable/repaired app pair; pinned source and probe revisions; independent disposable runs; a model restricted to choosing reviewed checks; a deterministic verifier; request/response and provider receipts; and an explicit `inconclusive` state for unrun checks. That is a product packaging and trust advantage for the particular demo audience, **not a demonstrated technical superiority over competitors**. It becomes a product edge only if the team proves the workflow reliably, quickly, and cheaply and later offers it for a user's own authorized repository. The existing [PRD](prd-vibesec.md), [SDD](sdd-vibesec.md), and [state](state.md) describe the full workflow as draft behavior. A local synthetic fixture and fixed comparison now run; remote isolation, model planning, receipts, and cost remain unproved.

There is also a serious **name collision**: OX Security markets a commercial product called **OX VibeSec**, and at least three other public scanners use VibeSec. The closest labels even target AI-built apps. Consider a distinct public name before the demo, README promotion, package publication, or domain purchase. This is a search-based branding concern, not a trademark clearance or legal opinion. [OX product](https://www.ox.security/vibesec/), [OX docs](https://docs.ox.security/vibesec/vibesec), [Python VibeSec](https://github.com/AyushkhatiDev/vibesec), [web VibeSec](https://github.com/mylee04/vibesec), [VibeSec Network](https://www.vibesec.network/docs/getting-started).

## How to read this comparison

“Documented” means the vendor or maintainer publishes a feature, implementation, requirement, or limitation. It is **not independent proof of detection rate, false-positive rate, customer outcomes, or current service availability**. “Inference” marks our interpretation. The comparison is current as of the date above. No competitor scans or paid accounts were run. Features absent from a public page are marked *not established by reviewed sources*, never “does not exist.”

## What to copy, avoid, and actually differentiate

1. **Copy the evidence discipline, not the “autonomous hacker” positioning.** Competitors already show exploit traces. For the hackathon, show the exact identity and object boundary, the recorded request, the precise synthetic canary that crossed it, and the repaired response. Keep the model's plan separate from the verifier's verdict. [XBOW reports](https://docs.xbow.com/console/reference/reports/), [Shannon safety](https://github.com/KeygraphHQ/shannon/blob/main/docs/safety.md), [local PRD](prd-vibesec.md).
2. **Make coverage and failure as visible as success.** Show selected probes, executed probes, skipped probes, timeouts, cleanup status, model ID, token use and Sandbox receipt, plus a clear “not reproduced in this comparison” rather than “secure.” This responds to a real interpretability issue that [Strix's own guidance](https://github.com/usestrix/strix/blob/main/skills/penetration-testing-with-strix/SKILL.md) acknowledges; it is a design opportunity, not a claim Strix hides coverage. [Local PRD](prd-vibesec.md).
3. **Use immutable, independent experiment inputs.** Pin fixture and probe revisions, start each attempt from the same saved baseline, and rerun the exact plan against the repaired pair. Test that branches do not share writes and that the app restarts correctly. This is the most concrete way to make the demo repeatable; its feasibility is still unproven and needs the [runtime proof](research-vibesec.md).
4. **Offer one-click comprehension for the judge.** Preselect the owned fixture, explain what two synthetic users mean, and expose a short before/after view. That accessibility is likely useful because enterprise scans require target, auth, scope, and sometimes server setup. It is an **inference from the documented setup paths**, and the team should user-test it. [StackHawk setup](https://docs.stackhawk.com/hawkscan/), [Burp CI setup](https://portswigger.net/burp/documentation/dast/user-guide/ci-cd/ci-driven-scans/create-config), [VibeSec PRD](prd-vibesec.md).
5. **Position a future own-repo mode as an extension, not today's capability.** Later, accept a pinned authorized repository, require a reproducible local app launch and test identities, constrain network/scope, allow custom app-specific invariants, then export a replayable report to CI. This is a hypothesis for discovery, not a feature to claim now; Strix, Shannon, StackHawk, and Burp already support variants of repository, API, and CI workflows. [Strix CLI](https://github.com/usestrix/strix/blob/main/docs/usage/cli.mdx), [Shannon README](https://github.com/KeygraphHQ/shannon/blob/main/README.md), [StackHawk docs](https://docs.stackhawk.com/hawkscan/), [Burp CI](https://portswigger.net/burp/documentation/dast/user-guide/ci-cd/ci-driven-scans).

## Recommended first-release claim and proof bar

**Proposed claim:** “Run a controlled security experiment against a disposable AI-built app, inspect the evidence for a cross-user data leak, and replay the same check after a repair.” Avoid “first,” “zero false positives,” “production-ready pentest,” “proves your app is secure,” and generic “autonomous penetration testing platform.” The first claim is narrow enough to verify and does not imply broad coverage.

**Proof before public demo:** (a) vulnerable fixture returns the canary to the wrong user; (b) repaired fixture blocks that same request; (c) branch write independence and cleanup are shown with provider receipts; (d) one live Nebius-served NVIDIA model chooses an allowlisted plan that passes policy validation; (e) malformed or adversarial plan text cannot dispatch an unknown probe; (f) timeout, failed model call and skipped attempts yield conspicuous incomplete reports; (g) real duration, token and Sandbox usage are measured. These are acceptance targets drawn from the [PRD](prd-vibesec.md), [QA plan](qad-vibesec.md), and [feasibility note](research-vibesec.md), not achieved outcomes.

**Comparison experiment:** On the same local synthetic app, run one open-source baseline such as ZAP or Strix if time and access permit. Record setup time, cost, exact canary finding, controls, false claims, and report clarity. Do not treat a single fixture as a general benchmark. This would provide defensible “what worked for us” evidence and useful Nebius friction feedback; the market review alone cannot do that.
